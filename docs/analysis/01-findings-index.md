Every finding from the twelve-dimension review of the NicePay Payment Gateway plugin, in one table. The review produced **489 findings that survived adversarial verification**, recorded across eleven dimension documents as **484 numbered entries** — the architecture and UX documents each fold a small number of near-identical findings into a single numbered entry rather than repeating them. Two claims were **refuted outright** during verification and are listed at the end, together with the significant *sub-claims* that were killed inside findings that otherwise survived. Nothing here is new analysis: this document is a navigation surface over documents 02–12, and every row links to the full write-up, evidence and recommendation.

## How to read this table

| Column | Meaning |
|---|---|
| **ID** | Stable finding identifier; links to the full entry in its dimension document. |
| **Dimension** | Which of the twelve review dimensions produced it. |
| **Finding** | One-line statement of the defect or gap. |
| **Primary location** | The single most representative `file:line`. Most findings cite several; the dimension document has the full list. |
| **Effort** | Fix size as estimated by the reviewer: `trivial` (< 1 h) · `small` (a few hours) · `medium` (1–3 days) · `large` (a week or more). |
| **Verdict** | `CONFIRMED` — the verifier reproduced the code observation directly. `PLAUSIBLE` — the code observation holds but the stated consequence depends on live NICEPAY behaviour, a running WordPress/WooCommerce instance, or a browser runtime that was not available. **Treat every PLAUSIBLE row as needing confirmation before you act on it.** |

Severity is the section heading. Within each severity, rows are grouped by dimension in document order (Protocol → Payment flow → Security → UX → WP/WC platform → Architecture → i18n → Testing → Documentation → Release → Excellence).

> **A note on the `PLAUSIBLE` rows.** No PHP runtime, WordPress installation, WooCommerce instance or NICEPAY sandbox account was available during this review. Every code quotation was read from the working tree at branch `main`. Where a finding's consequence depends on something outside the repository — how NICEPAY formats a response field, how a browser handles a cross-site cookie, how WooCommerce resolves an order status — the verifier marked it PLAUSIBLE rather than asserting it. The whole of document 12 falls into this category by construction.

## Refuted during verification

Two findings raised by dimension reviewers were **killed outright** by the verification pass and appear in no dimension document. They are recorded here so they are not re-raised by a future reader who notices the same code shape.

| # | Dimension | Claim as raised | Why it was killed |
|---|---|---|---|
| R-1 | Protocol | The approval and cancel Signatures are verified against the PG-echoed `Amt` with no equality check against the requested `Amt`, so a zero-padded `Amt` (`000000001004`) would fail verification against a signature computed over the unpadded value — making every payment fail and then be net-cancelled. | The **code observation is true** and survives as [PROTOCOL-13](02-protocol-conformance.md) / [FLOW-13](03-payment-flow-and-money-correctness.md) / [CODE-12](07-architecture-and-code-quality.md) in reduced form. The **consequence was refuted**: the plugin's `TID + MID + response-Amt + MerchantKey` construction is verbatim NICEPAY's own published sample pattern, which would be broken for every NICEPAY merchant if the PG padded the response `Amt`. The spec digest flags the padding as *something to verify*, not as vendor-stated behaviour, and `Amt(12)` reads as a maximum field width. No sandbox was available to settle it. **One question settles it permanently: has a single live payment ever completed through this plugin?** If yes, the hypothesis is dead. |
| R-2 | Customer UX | Two `[nicepay_payment]` shortcodes on one page cause the second inline `<script>` to re-initialise `var _nicepayModalEscHandlers = {}`, orphaning the first modal's document-level `keydown` listener. | **Refuted as stated.** All inline `<script>` blocks on a page are parsed and executed during initial document parsing — long before a user can click a trigger — so the registry has finished re-initialising before any handler is ever stored. No code path in this plugin injects a shortcode instance after load. The residual (duplicated script weight, N-times listener registration) survives at LOW severity as [UX-108](05-user-experience.md). |

## Sub-claims refuted inside surviving findings

These findings survived, but a specific claim inside each one did not. They are listed because each is a plausible-sounding conclusion a future reader could reach independently — and each is wrong.

| Finding | Refuted sub-claim | Correction |
|---|---|---|
| [PLATFORM-09](06-wordpress-woocommerce-platform.md) / [CODE-11](07-architecture-and-code-quality.md) | "`PRIMARY KEY (id)` uses one space where dbDelta requires two, causing repeated ALTER attempts." | Obsolete folklore. dbDelta's index parser was rewritten in WP 4.2 to accept `\s+` with an optional name group; single-space `PRIMARY KEY (id)` parses correctly on every version this plugin supports (WP 5.0+). Do **not** make this change. The `CREATE TABLE IF NOT EXISTS` half of the finding is real. |
| [PROTOCOL-22](02-protocol-conformance.md) / [FLOW-20](03-payment-flow-and-money-correctness.md) | "A failed NicePay return empties the shopper's cart, forcing them to rebuild it." | `wc_clear_cart_after_payment()` explicitly skips orders in `failed`/`pending`/`cancelled` state, so the cart survives. The real costs are the spurious failed-order email and the redirect to `wc_get_checkout_url()` instead of `$order->get_checkout_payment_url()`. |
| [FLOW-15](03-payment-flow-and-money-correctness.md) / [PLATFORM-04](06-wordpress-woocommerce-platform.md) | "After an admin cancel the order still reports its full total as revenue in WooCommerce Analytics." | Analytics excludes `cancelled` from gross revenue by default, so the sale disappears rather than double-counting. The genuine defects are the missing `WC_Order_Refund` object, the absent customer notification, and the silent restock. |
| [SECURITY-09](04-security.md) / [FLOW-18](03-payment-flow-and-money-correctness.md) | "Two checkouts in the same second collide with p ≈ 1/9,000 and a payment can be attributed to the wrong order." | False for the WooCommerce path: `generate_moid( 'WC' . $order->get_id() )` makes the prefix order-unique, so cross-order collision is impossible. The risk is confined to the standalone flow, whose prefix is the constant `'SP'`. |
| [FLOW-10](03-payment-flow-and-money-correctness.md) | "A 19.99 EUR cart becomes a 19 KRW charge." | `nicepay_get_amount()` only truncates when `$currency === 'KRW'`; EUR returns `"19.99"`. The outcome is a payment rejected at the PG, not a 1000× underpayment. |
| [FLOW-25](03-payment-flow-and-money-correctness.md) | "`CcPartCl` and `ClickpayCl` are received and discarded." | The entire approval response is persisted as JSON in the `payment_data` column. The data is already stored; only the *read* and the pre-flight check are missing, which makes the fix far cheaper than stated. |
| [SECURITY-14](04-security.md) | "Neither existing callback endpoint applies a source-IP check." | Not a defect. Both existing endpoints receive a **browser** POST (`document.payForm.submit()`), so an IP allowlist there would break every payment. The documented inbound IPs apply only to the deposit-notification endpoint — which does not exist yet. |
| [PLATFORM-11](06-wordpress-woocommerce-platform.md) | "Under HPOS the `post.php?post=` link can open an unrelated post that happens to share the ID." | HPOS reserves order IDs by writing `shop_order_placehold` rows into `wp_posts` precisely so IDs never collide. The link errors out; it does not misdirect. |
| [PLATFORM-05](06-wordpress-woocommerce-platform.md) / [UX-012](05-user-experience.md) | "Plain permalinks are still the WordPress default on a fresh install." | `wp_install()` has selected a date/name permalink structure for new non-multisite installs since WP 4.2 where rewrites are available. The 404 is real but configuration-conditional. |
| [UX-092](05-user-experience.md) | "The status badge visibly changes case after a cancel because two different msgids are used." | `.nicepay-status { text-transform: uppercase }` normalises both paths, and ko_KR translates both msgids identically. Only `tr_TR` differs, on the Turkish dotted/dotless I. The four hardcoded English strings in the admin JS are the real, surviving half. |
| [UX-097](05-user-experience.md) / [UX-114](05-user-experience.md) | "A pulsing `.nicepay-status-waiting` dot animates on the customer's result page." | That class is emitted only by the admin transactions table. The customer-facing reduced-motion gap is real; this specific scenario cannot occur. |
| [UX-065](05-user-experience.md) | "The selected payment method is signalled by hue alone (WCAG 1.4.1)." | The selected state also changes shape (2 px ring → 5 px dot) and weight (500 → 600). The genuine failure is the **unselected** boundary at 1.24:1 and the placeholder text at 2.54:1. |
| [SECURITY-22](04-security.md) | Recommended fix: `wp_remote_post( $url, [ 'timeout' => 30, 'connect_timeout' => 5 ] )`. | `WP_Http::request()` assembles transport options from a fixed key list and does not forward an arbitrary `connect_timeout` argument — the suggested fix would silently do nothing. Use an `http_api_curl` filter setting `CURLOPT_CONNECTTIMEOUT`. |
| [PLATFORM-15](06-wordpress-woocommerce-platform.md) / [DOCS-029](10-documentation.md) | "The documented `remove_action` snippet fails because the gateway registry is not built at `init`." | Wrong cause: the plugin registers its `woocommerce_payment_gateways` filter on `plugins_loaded` priority 11, which precedes `init`. The actual defect is the unguarded `['nicepay']` index on an *available-only* gateway list. |
| [FLOW-16](03-payment-flow-and-money-correctness.md) | "Duplicate pending rows mean refunds can target the wrong reference." | `process_refund()` identifies the payment by `_nicepay_tid`, written from the attempt that actually succeeded. The real harms are table pollution and the concurrent-attempt surface. |
| [UX-096](05-user-experience.md) / [I18N-10](08-internationalization.md) | Recommended fix: swap `nicepay_format_amount()` to return `wc_price()`. | `wc_price()` returns HTML and all six call sites wrap the result in `esc_html()` — the drop-in would print raw `<span class="woocommerce-Price-amount">` markup to users. Keep the function returning plain text. |
